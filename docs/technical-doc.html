01项目概述

1.1 背景

一个站在帕特农神庙前的旅行者，通常能看到的只有“石头”：一堆柱子、一段台阶、一片残破的山花。他很少知道，这些柱子的比例是给一位处女神量出来的；台基中央故意上凸、角柱故意加粗，是为了对抗人眼的错觉。

神话解释“为什么建”，建筑记录“怎么建”，而这两件事在通行资料里通常被分开讲述：神话读物止步于故事，建筑史止步于形制。结果是—— 读者知道了宙斯的故事，却不知道奥林匹亚那座神庙的柱子为什么是六根；知道了封禅，却不知道天贶殿为什么用重檐歇山。

本项目的出发点很具体：把“神话 → 圣地 → 建筑形制”缝成一条可以走完的线。每一个神话节点，最终都要落在一处真实存在的建筑构件上： 柱式、屋顶、轴线、材料、朝向。没有泛泛的“值得一去”，只有“站在这里抬头看什么”。

03系统架构设计

3.1 总体形态

整个系统由两部分组成：一个 2.3 MB 的 HTML 文件（含四卷界面、旅人整站、36 张内联照片）与 一个 Serverless 函数（Dify 代理）。前者是纯静态资源，后者只在用户提问时被调用。

3.2 四卷状态机

四个版面均为绝对定位叠放，切换由唯一的 go(i) 收敛：设 .is-active、更新圆点、页码、翻页按钮禁用态， 并在 i === 3 时按需装载旅人。没有额外的路由层，?page=N 仅用于深链调试。 

function go(i) {
  i = Math.max(0, Math.min(plates.length - 1, i));
  if (i !== 0) unlockSphere();                       // 离开星穹时把球体复位
  plates.forEach((p, k) => p.classList.toggle('is-active', k === i));
  dots / tabs / pgCount / prevBtn / nextBtn 同步;
  current = i;
  if (i === 3 && !journeyPid && !bootingJourney) ensureJourney(null);
}

3.3 边界隔离：为什么卷四用 iframe

旅人（独立开发阶段的三幕应用）与图志各自都占用了 $、.btn、.stage、body 等全局名， CSS 变量 --ease、--ink 也重名。硬合并需要对 4000+ 行脚本做命名空间化、对 850 行样式加前缀，风险高。

因此采用同源 iframe + srcdoc：旅人源码以 <script type="text/template"> 存放，进卷四时还原、按谱系打补丁、写入 iframe。 iframe 铺满版面区域（padding:0; perspective:none），视觉上就是一卷图版；同时图志顶栏保持唯一 chrome。

三个必须处理的细节

① 脚本数据转义：模块内容里的 </script 与 <!-- 必须转义为 <\/script、<\!--—— 否则脚本数据进入 escaped / double-escaped 状态，块尾的闭合标签失效，整个文档会被吞进模板块。
② 两套顶栏：注入 .bar{display:none} 隐藏旅人自带导航，避免双顶栏。
③ 按需装载与去重：journeyPid 记录当前装载内容，切走再回来不重载 1.2 MB 文档。

3.4 渲染管线

层级技术关键实现
星穹Canvas 2D + DOM 混合星野与经纬线用 Path2D 分批描边；星标是绝对定位的 DOM 按钮，与 canvas 共用投影函数
圣殿CSS 3D（preserve-3d）仅三个原语 box() / panel() / face()，曲面屋顶另加 wedge() 逐面旋转

图版手绘 SVG36 幅节点线刻，统一 200×210 视框与描边参数

04AI 技术方案

本章是评审核对重点：先说明任务与选型理由，再说明集成方式，最后给出可量化的优化策略与评测方式。

4.1 任务定义

用户的问题高度集中在“具体遗址的具体构件”上，例如：帕特农神庙为什么故意做得不直？金字塔的朝向和太阳神信仰有关吗？Newgrange 的冬至光是怎么进来的？ 这类问题的共同特征是：答案需要落在可核对的具体事实上（尺寸、方位、年代、构造做法），而不是开放式创作。

维度判断
任务类型闭卷事实型问答（closed-book QA → 检索增强）
知识来源项目自建的 36 站图志 + 典籍与考古资料摘要（约 5 万字）
失败代价高。幻觉出一个尺寸或年代，直接摧毁站点的可信度
交互形态多轮对话，允许追问（“那角柱加粗是为什么？”）
语言中文为主，保留原文专名（Parthenon / Hor-em-akhet）

4.2 选型理由

候选方案有三条，逐一比较后选择 C：

方案优点缺点结论
A. 直接调大模型（无检索）最快接入，代码极少幻觉率高；无法引用自建内容；说错尺寸无从纠正不采用
B. 自建 RAG（向量库 + 编排）完全可控，可深度定制召回与重排需向量库、嵌入模型、编排服务与运维；与“零依赖、无自建后端”的项目约束冲突不采用
C. Dify 知识库应用 + 自建代理检索、切分、提示词、会话在平台内配置；对外只暴露一个 HTTP 接口；可随时换模型依赖第三方；需要一层代理来隔离密钥与限流采用

选 C 的核心理由是把“AI 能力”当作可替换的外部服务，而不是站点的一部分。项目本身的价值在内容结构与交互形态， 不应把工程预算消耗在向量库运维上；同时 Dify 提供了 retriever_resources（命中片段元数据）， 使“答案 → 原文出处”的回链成为可能——这是纯调用大模型做不到的。

与项目约束的一致性

零外部依赖 → AI 走服务端，前端不加载任何 SDK；
密钥不下发 → 前端只请求同源 /api/chat，Key 在函数进程内读取；
断网可用 → 未配置或请求失败时自动降级为内置词条，浏览与阅读不受影响。

4.3 知识库构建

环节做法理由
语料来源36 站图志正文 + 典籍摘录 + 考古与建筑史要点与页面内容同源，保证“问到的”与“读到的”一致
切分策略按“一站一文档”，单文档 400–800 字；长条目按小标题二次切分问答多以单点为主，过度切分会丢失上下文
元数据每段带 domain（六域）、site（站名）、code（图版编号）用于过滤召回与结果回链
专名处理保留原文拼写并给中文对照（Hor-em-akhet / 地平线上的荷鲁斯）用户两种写法都能命中
更新方式内容改版后重跑一次索引；页面侧无需改动知识与展示解耦

4.4 集成方式

请求契约

// 前端 → 代理
POST /api/chat
{ "query": "帕特农神庙为什么故意做得不直？", "conversation_id": "", "user": "mythos-web" }

// 代理 → Dify
{ "inputs": {}, "query": "…", "response_mode": "blocking",
  "conversation_id": "", "user": "mythos-web" }

// 代理 → 前端（归一化后）
{ "answer": "…", "conversation_id": "3f2a…", "sources": [{ "code": "GR-01" }] }

多轮与上下文

conversation_id 由 Dify 首次返回、前端保存并在后续请求回传，从而支持“那角柱加粗是为什么”这类省略主语的追问。 user 固定为 mythos-web，不使用个人标识——既不采集隐私，也便于在 Dify 侧按应用维度看调用量。

4.5 提示词与输出约束

约束目的
只依据检索片段回答抑制幻觉；片段里没有的就明说“本志未收”
结构化输出：结论 + 依据 + 出处编号让用户能回到图版核对
数值必须带单位与量级“69.5 × 30.9 米”而不是“大约七十米”
禁止编造未收录的遗址站点只对 36 处负责，避免答成旅游百科
答案长度 ≤ 300 字适配抽屉式阅读面板，避免长文把界面撑爆

4.6 优化策略

策略具体做法效果
检索范围收敛按 domain 元数据先过滤再召回避免“中国的问题答成希腊的柱式”
查询改写把口语化提问补全专名（“那个圆土丘”→ Newgrange）提升召回率，减少“不知道你指哪”
结果归一化代理层把 retriever_resources 解析为图版编号前端可直接渲染“出处 GR-01”并可点击
超时与中断前端 30 s AbortController；给用户明确的等待态杜绝无限转圈
降级链直连 → 代理 → 本地词条任何环节故障都不白屏
限流同 IP 30 次/分，超限返回 429防止密钥被刷、控制调用成本
体积与首屏解耦AI 不参与首屏；函数冷启动不影响浏览弱网下先读到内容，再答问题

4.7 评测方式

自建 40 题的小型评测集，覆盖六个域、四类问法（尺寸 / 方位 / 构造 / 源流），逐题人工核对三点： 事实是否正确（对照正文）、是否给出出处、是否仅依据检索片段。

指标定义目标
事实准确率关键数值/结论与正文一致≥ 95%
出处覆盖率答案带可回链的图版编号≥ 90%
拒答正确率未收录问题明确说明未收录≥ 90%
P95 响应从提交到首字返回< 8 s

评测在部署环境执行，结果随版本记录；改动知识库或提示词后需重跑。

4.8 安全与合规

  • 密钥：只存平台环境变量；源码经自检脚本扫描，确认无 app- 开头的密钥串。
  • 输入：代理层对 query 截断至 2000 字符，不落库、不记日志正文。
  • 输出：只透传 answer 与出处编号，不返回原始检索片段，避免二次泄漏。
  • 来源：可用 ALLOW_ORIGIN 收窄到自有域名，阻断第三方盗用代理。

05核心功能实现

5.1 星穹：canvas 与 DOM 的混合

星野、经纬线与大气光晕由 canvas 绘制；星标不是画上去的，而是绝对定位的 DOM 按钮——可聚焦、可键盘操作、可挂提示，点击热区也好控。 两者共用同一个 project(lat, lon) 投影函数，保证“球转星标跟”。

锁定某个谱系时给球体容器施加 rotateY 位移与缩放，镜头转向该节点；标签做矩形相交检测防重叠，按 z 轴深度排序后再放置， 解决早期移动端的抖动。

5.2 圣殿：三个原语拼出六座建筑

不引入 3D 引擎，只抽象出三个原语，所有建筑都由它们拼装： 

box(w, h, d, x, y, z, {front, sideR, sideL, top})   // 长方体，y 是底边
panel(w, h, x, yBottom, z, rotY, cls, extra)        // 单片面板
face(w, h, transform, cls)                          // 单个面

关键坑：CSS 权重

基础规则 .b>i{background:#c9bea9} 的特异性为 (0,1,1)，会覆盖材质类 .f-xxx (0,1,0)， 导致整栋建筑变成一片米色。所有材质类必须写成 .b .f-xxx（(0,2,0)）才生效。此坑排查耗时最长，已写入文档与注释。

5.3 地图：等距投影与行走

  • 世界容器施加 rotateX(58deg) rotateZ(-30deg) 形成等距视角；节点与人物反向旋转做 billboard，避免被压扁。
  • 路径由 36 站坐标经 Catmull-Rom 平滑成曲线（catmullD），人物用 getPointAtLength 沿路径推进。
  • 相机对位必须计入透视：w = 1 - z/1400，cam.ty = oyL + (offY - oyL) * w；按纯 2D 线性计算会偏 200 像素以上。
  • 地形（河流、山脉、岛屿、长城）由固定随机种子的程序化 SVG 生成，可复现、可微调。

5.4 图志：把神话落到构件上

每站卡片包含四段：神话叙述（约 150 字，讲清神的行动与人的处境）、三条建筑形制（具体到数字与做法）、 起源地推荐（站到那里该看什么）、实景照片（带图注与许可）。正文刻意保留可核对的数字： “柱高 10.4 米、台基 69.5 × 30.9 米”“Ménec 石列长 1167 米、11 行、1099 块”。

07创新点说明

7.1 技术创新

（1）零依赖的“单文件全站”架构

把四卷界面、六域 36 站、36 张真实照片、六座 3D 建筑、六套地形全部压进一个 HTML 文件，运行时不产生任何外部请求。 这在传播与评审场景下非常关键：一个文件即可完整演示，无需部署、无需安装、无需网络。 为实现这一点，项目自建了两套配套机制——照片的内联压缩流水线（640 px / ≤20 KB / 质量二分搜索）与模板块的转义装载器。

（2）CSS 3D 的参数化建筑生成器

六座圣殿并非贴图或模型文件，而是由三个原语（box / panel / face）加一个斜屋面算子 wedge 现场拼装： 帕特农的围廊、天贶殿的重檐、伊势的千木、纽格莱奇的穹丘、巨石阵的柱列，全部可由参数描述并在源码中直接读到。 这带来两个好处：体积为零（无模型文件），可读性极高（评委可直接读懂一座建筑是怎么被“搭”出来的）。

（3）应用内嵌应用的边界方案

两套各自成熟的前端应用要在同一页面共存，常规做法是重写命名空间或引入微前端框架。项目给出第三条路： 模板块存放 + 运行时还原 + srcdoc 隔离，并用“转义 </script 与 <!--”解决脚本数据状态的解析陷阱。 结果是零冲突、零依赖，且能用 enterChapter(pid) 精确控制内嵌应用的初始状态。

（4）等距地图的相机与行走

在纯 CSS 3D 下实现“人物沿路径行走 + 相机跟随”，难点在于透视对位：必须把 w = 1 - z/1400 代入屏幕坐标换算， 否则镜头会偏出 200 像素以上。项目把这一推导固化为公式并写入注释，使后续新增域时无需重新调参。

（5）密钥零暴露与三级降级

前端不保存任何密钥，只请求同源代理；代理带限流与来源白名单。同时设计“直连 → 代理 → 本地词条”三级降级， 保证 AI 链路任何一环失效时，站点依然是完整的读物而非错误页。

7.2 应用创新

（1）“神话—圣地—建筑形制”三段式解说

通行资料里神话与建筑史是两条线。本项目把每一条神话节点都落到具体构件上：波塞冬与雅典娜之争 → 帕特农的多立克围廊与视差矫正； 大国主让国 → 出云大社的心御柱与 5.2 米注连绳；达格达的居所 → 纽格莱奇的屋顶箱与冬至光。 读者不是“知道了一个故事”，而是知道下次站在那栋建筑前该抬头看哪里。

（2）问答与图版的闭环

AI 答案通过 retriever_resources 回链到图版编号（如 GR-01），用户可以从一句回答直接跳到那一站的实景与形制说明。 “问 → 读 → 走”形成闭环，AI 不是外挂的聊天框，而是索引器。

（3）跨文明的横向对照

六域共用同一套数据模型与坐标网格，使“同一母题的不同处理”可以被直接比较： 墓葬（金字塔 / 通道墓 / 王陵 / 古坟）、门（塔门 / 鸟居 / 山门 / 石圈入口）、柱（多立克 / 纸莎草 / 朱漆 / 立石）。 这种对照在单文明读物里几乎不会出现。

（4）为评审与传播而设计的交付形态

一个 2.3 MB 的文件可以走邮件、U 盘、IM；学校机房、无网会议室都能直接打开演示。 对参赛作品而言，“能被打开”本身就是一项被低估的创新。

8.1 完成情况

项目完成了一个可交付、可演示、可传播的世界神话史站点：六域 36 站、四卷交互、六座程序化圣殿、36 张真实实景， 并接入检索增强问答。全部代码与素材在一个仓库内，含完整提交历史、架构文档、素材授权清单与自检脚本。

8.2 局限

  • 体积：2.3 MB 对移动网络仍是负担，首屏需要解析整份文档。
  • 模型细节：CSS 3D 停留在体量与主要构件层面，石材肌理、雕饰、内部空间无法表达。
  • 知识边界：问答只对 36 站负责，超出范围会明示未收录——这是有意的克制，但对部分用户可能显得“不够聪明”。
  • 内容维护：目前靠人工撰写与核对，尚未建立更系统的资料引用体系。

8.4 结语

这个项目试图回答一个小问题：当一个人终于站在那些石头面前，能不能提前知道该抬头看哪里。 技术上它没有用最时髦的方案，而是把“零依赖、可读、可传播”当作硬约束，用 CSS 3D、canvas 与一个代理函数把答案做了出来。 如果它能让某个人在帕特农的柱廊前多站三分钟，这个项目就成立了。
